1. PURPOSE
----------
This specification defines the test cases used to validate the Impact Analyzer
component of the Change-Propagation system. Each test case simulates a realistic
AUTOSAR requirement change, verifies that the Impact Analyzer correctly identifies
all affected CanIf.c functions via the TM, and provides a precise code mutation
that serves as the ground-truth evidence of where the change manifests in code.

2. SYSTEM UNDER TEST
--------------------
  Input  : Delta-Detector output — one or more changed Req IDs with change type
  Lookup : REQ-CODE-TM.txt — maps Req ID → CanIf.c function(s)
  Output : Set of CanIf.c functions impacted by the requirement change(s)

  Pass criterion (default): The analyzer output set EXACTLY MATCHES the
  TM-predicted set for each changed Req ID in the scenario. No missing functions;
  no extra functions.

3. CHANGE CATEGORIES
---------------------
  FUNCTIONAL   (F)    : Change in behavioral logic — algorithm, control flow,
                        error code, return value, or called API. Code MUST change.

  NON-FUNCTIONAL (NF) : Change in interface contract with no behavioral logic
                        change — data type width, naming convention, AUTOSAR
                        version alignment, SduLength range boundary. Code MUST
                        change but runtime behavior for valid inputs is unchanged.

  COSMETIC (C)        : Wording, cross-reference number, editorial clarification.
                        NO code change required. Impact Analyzer still flags the
                        function; human engineer review closes with "no action".

  CROSS-DEPEND 1→N (XD-1N) : One requirement change propagates to N >= 2
                        distinct CanIf.c functions.

  CROSS-DEPEND N→1 (XD-N1) : N >= 2 requirement changes all propagate to the
                        same single CanIf.c function. Analyzer must aggregate.

  COMBINED (CB)       : A realistic sprint containing simultaneous changes of
                        multiple categories across multiple functions.

4. MUTATION CONVENTION
-----------------------
  Each test case with a Functional or Non-functional category provides an
  EXACT CODE MUTATION: the precise old string → new string to apply in CanIf.c
  to create the ground-truth test fixture. Cosmetic cases carry NO mutation.
  Apply mutations ONE TEST CASE AT A TIME and revert after each run to keep
  CanIf.c in a clean state between executions.

  Notation used:
    FILE  : Relative path from project root
    LINE  : Line number in the file at the time of this specification
    OLD   : The exact existing code string to replace
    NEW   : The replacement string representing the mutated requirement

TC-IMP-F-01
────────────────────────────────────────────────────────────────────────────────
Title          : Functional — SetControllerMode calls wrong CAN Driver API
Category       : FUNCTIONAL
AUTOSAR Req ID : SWS_CANIF_00308
Req (Original) : "The service CanIf_SetControllerMode() shall call
                  Can_SetControllerMode(Controller, Transition) for the
                  requested CAN controller."
Simulated Change: Requirement is revised to mandate a new intermediate wrapper:
                  "CanIf_SetControllerMode() shall call Can_InitController()
                  instead of Can_SetControllerMode() for every transition."
TM Prediction  : CanIf_SetControllerMode
Expected Output: { CanIf_SetControllerMode }

Code Mutation:
  FILE : OpenSAR/communication/CanIf/CanIf.c
  --- MUTATION 1 (line 253) ---
  OLD : if (Can_SetControllerMode(canControllerId, CAN_T_STOP) == CAN_NOT_OK){
  NEW : if (Can_InitController(canControllerId, 0) == CAN_NOT_OK){

  --- MUTATION 2 (line 264) ---
  OLD : if (Can_SetControllerMode(canControllerId, CAN_T_START) == CAN_NOT_OK){
  NEW : if (Can_InitController(canControllerId, 0) == CAN_NOT_OK){

  --- MUTATION 3 (line 275) ---
  OLD : if (Can_SetControllerMode(canControllerId, CAN_T_STOP) == CAN_NOT_OK){
  NEW : if (Can_InitController(canControllerId, 0) == CAN_NOT_OK){

  --- MUTATION 4 (line 285) ---
  OLD : if (Can_SetControllerMode(canControllerId, CAN_T_SLEEP) == CAN_NOT_OK){
  NEW : if (Can_InitController(canControllerId, 0) == CAN_NOT_OK){

  --- MUTATION 5 (line 296) ---
  OLD : if (Can_SetControllerMode(canControllerId, CAN_T_WAKEUP) == CAN_NOT_OK){
  NEW : if (Can_InitController(canControllerId, 0) == CAN_NOT_OK){

  --- MUTATION 6 (line 306) ---
  OLD : if (Can_SetControllerMode(canControllerId, CAN_T_STOP) == CAN_NOT_OK){
  NEW : if (Can_InitController(canControllerId, 0) == CAN_NOT_OK){

Pass Criterion : Analyzer output == { CanIf_SetControllerMode } — exactly one
                 function flagged, matching TM entry for SWS_CANIF_00308.
AUTOSAR Note   : Can_SetControllerMode is the normative CanDrv API per
                 SWS_Can_00017. Replacing it with Can_InitController violates
                 the CanIf–CanDrv interface contract and breaks all state
                 transitions.

TC-IMP-XD1N-01
────────────────────────────────────────────────────────────────────────────────
Title          : Cross-depend 1→2 — One req change propagates to two functions
Category       : CROSS-DEPEND (1 Req → N Functions)
AUTOSAR Req ID : SWS_CANIF_00866
Req (Original) : "If CanIf_SetControllerMode(ControllerId, CAN_CS_STOPPED) or
                  CanIf_ControllerBusOff(ControllerId) is called, CanIf shall
                  set the PDU channel mode of the corresponding channel to
                  CANIF_TX_OFFLINE."
Simulated Change: Mode changed to CANIF_OFFLINE — "both events shall now take
                  the channel fully offline (no Rx either) rather than
                  TX-offline-only."
TM Prediction  : CanIf_SetControllerMode, CanIf_ControllerBusOff
Expected Output: { CanIf_SetControllerMode, CanIf_ControllerBusOff }

Code Mutation:
  FILE : OpenSAR/communication/CanIf/CanIf.c

  --- MUTATION in CanIf_SetControllerMode (line 305) ---
  Context: CANIF_CS_STOPPED case sets PDU mode
  OLD  : CanIf_SetPduMode(channel, CANIF_SET_OFFLINE);
  NEW  : CanIf_SetPduMode(channel, CANIF_SET_ONLINE);
  (wrong mode injected to represent the behavioral change)

  --- NOTE on CanIf_ControllerBusOff ---
  CanIf_ControllerBusOff() (line 935) calls:
      CanIf_SetControllerMode(channel, CANIF_CS_STOPPED);
  which internally triggers the mutated PDU mode set above.
  Therefore CanIf_ControllerBusOff is impacted transitively via the same
  requirement. The TM correctly lists both functions for SWS_CANIF_00866.

Pass Criterion : Analyzer output == { CanIf_SetControllerMode,
                                      CanIf_ControllerBusOff }.
                 Both functions must be returned. Returning only one is a FAIL.
AUTOSAR Note   : This is the canonical 1→N cross-dependency scenario. The
                 requirement text explicitly names two triggering functions,
                 which is why the TM maps one Req ID to two functions. The
                 analyzer must not resolve only the first match and stop.

Title          : Cross-depend N→1 — Two reqs changed, same function impacted
Category       : CROSS-DEPEND (N Reqs → 1 Function)
AUTOSAR Req IDs: SWS_CANIF_00311 + SWS_CANIF_00774
Req (Original):
  SWS_CANIF_00311: "Invalid ControllerId → CANIF_E_PARAM_CONTROLLERID"
  SWS_CANIF_00774: "Invalid ControllerMode (not CAN_CS_STARTED/SLEEP/STOPPED)
                    → CANIF_E_PARAM_CTRLMODE"
Simulated Change:
  SWS_CANIF_00311: Error code swapped to CANIF_E_PARAM_POINTER (copy-paste bug).
  SWS_CANIF_00774: ControllerMode validation removed — all values now accepted.
TM Prediction  : SWS_CANIF_00311 → CanIf_SetControllerMode
                 SWS_CANIF_00774 → CanIf_SetControllerMode
Expected Output: { CanIf_SetControllerMode }
                 (single function, aggregated from two independent req changes)

Code Mutation:
  FILE : OpenSAR/communication/CanIf/CanIf.c

  --- MUTATION 1 — SWS_CANIF_00311 (line 236) ---
  OLD  : VALIDATE( channel < CANIF_CHANNEL_CNT, CANIF_SET_CONTROLLER_MODE_ID, CANIF_E_PARAM_CONTROLLER );
  NEW  : VALIDATE( channel < CANIF_CHANNEL_CNT, CANIF_SET_CONTROLLER_MODE_ID, CANIF_E_PARAM_POINTER );

  --- MUTATION 2 — SWS_CANIF_00774 (lines 313-315) ---
  Context: Remove the CANIF_CS_UNINIT fall-through that acts as the invalid-mode
           catch (the switch default implicitly accepts all values in this impl).
  OLD  : case CANIF_CS_UNINIT:
           // Just fall through
           break;
  NEW  : case CANIF_CS_UNINIT:
         default:
           // All controller mode values now accepted — validation removed
           break;

Pass Criterion : Analyzer output == { CanIf_SetControllerMode }.
                 The function must be reported ONCE even though two requirements
                 triggered it. Duplicates in output are also a FAIL (idempotency
                 of set union must be enforced by the analyzer).
AUTOSAR Note   : N→1 tests the analyzer's result-set deduplication. In a real
                 change sprint, multiple reviewers may update different
                 requirements that trace to the same function. The developer
                 must receive ONE consolidated impact notice, not N duplicates.

Title          : Cross-depend N→1 — Three reqs changed, same function impacted
Category       : CROSS-DEPEND (N Reqs → 1 Function)
AUTOSAR Req IDs: SWS_CANIF_00389 + SWS_CANIF_00390 + SWS_CANIF_00902
Req (Original):
  SWS_CANIF_00389: "CanIf_RxIndication() shall process software filtering; if
                    rejected, the receive indication shall end."
  SWS_CANIF_00390: "After software filtering acceptance, CanIf shall process
                    the Data Length Check if configured."
  SWS_CANIF_00902: "Data Length Check shall be processed if enabled globally
                    AND not disabled per PDU."
Simulated Change:
  SWS_CANIF_00389: "Rejected frames shall be LOGGED before being dropped."
  SWS_CANIF_00390: "Data Length Check shall execute BEFORE software filtering."
  SWS_CANIF_00902: "Data Length Check is ALWAYS executed regardless of
                    CanIfPrivateDataLengthCheck and CanIfRxPduDataLengthCheck."
TM Prediction  : All three → CanIf_RxIndication
Expected Output: { CanIf_RxIndication }

Code Mutation:
  FILE : OpenSAR/communication/CanIf/CanIf.c

  --- MUTATION 1 — SWS_CANIF_00390 (reorder DLC before filter, ~line 800) ---
  Move the #if (CANIF_DLC_CHECK == STD_ON) block ABOVE the software filter
  block, so DLC is checked before the mask comparison runs.

  --- MUTATION 2 — SWS_CANIF_00902 (remove compile guard, ~line 823) ---
  OLD  : #if (CANIF_DLC_CHECK == STD_ON)
           if (CanDlc < entry->CanIfCanRxPduDlc)
           {
             VALIDATE_NO_RV(FALSE, CANIF_RXINDICATION_ID, CANIF_E_PARAM_DLC);
             return;
           }
         #endif
  NEW  :   if (CanDlc < entry->CanIfCanRxPduDlc)    /* always enforced */
           {
             VALIDATE_NO_RV(FALSE, CANIF_RXINDICATION_ID, CANIF_E_PARAM_DLC);
             return;
           }

  --- MUTATION 3 — SWS_CANIF_00389 (add log before drop, ~line 811) ---
  OLD  : entry++;
         continue; // Go to next entry
  NEW  : DET_REPORTERROR(MODULE_ID_CANIF, 0, CANIF_RXINDICATION_ID,
                          CANIF_E_PARAM_HRH);  /* log rejected frame */
         entry++;
         continue;

Pass Criterion : Analyzer output == { CanIf_RxIndication }.
                 Reported exactly once despite three independent requirement
                 changes. All three Req IDs must appear in the analyzer's
                 "contributing requirements" list attached to the impact report.
AUTOSAR Note   : This tests the analyzer's ability to process a batch of
                 correlated requirement changes and produce a single, clean
                 impact set with full traceability back to all source reqs.

Title          : Combined — Realistic sprint with four simultaneous req changes

Category       : COMBINED (F + NF + C + XD-1N)
AUTOSAR Req IDs: SWS_CANIF_00308 (F)
                 SWS_CANIF_00026 (NF)
                 SWS_CANIF_00423 (C)
                 SWS_CANIF_00073 (XD-1N)

Change Summary:
  SWS_CANIF_00308 [F]    : SetControllerMode calls wrong CAN API (see TC-F-01)
  SWS_CANIF_00026 [NF]   : DLC check changes to exact-match (see TC-NF-02)
  SWS_CANIF_00423 [C]    : Wording editorial update (see TC-C-01)
  SWS_CANIF_00073 [XD-1N]: OFFLINE mode no longer suppresses Rx (see TC-XD1N-02)

  SWS_CANIF_00308  →  CanIf_SetControllerMode

  SWS_CANIF_00423  →  CanIf_RxIndication      (cosmetic — no code action)
  SWS_CANIF_00073  →  CanIf_Transmit, CanIf_TxConfirmation, CanIf_RxIndication

  { CanIf_SetControllerMode, CanIf_Transmit,
    CanIf_TxConfirmation, CanIf_RxIndication }

  NOTE: CanIf_RxIndication appears in three req lookups (00026, 00423, 00073)

Code Mutations (apply all simultaneously for this scenario):
  See individual mutations from TC-IMP-F-01 (SWS_CANIF_00308 mutations),

                 multiple CRs in one sprint. The analyzer must handle all four
